- **2026-09-22** — **Root cause found for missing Google Pay AND Apple Pay buttons**: `GET https://api.sumup.com/v0.1/checkouts/{checkout_id}/payment-methods` (no auth needed) returned only `{"items":[{"id":"card"}]}` for our merchant — wallets are simply not enabled on the SumUp merchant account. The widget only renders what this endpoint returns. SumUp docs: "To enable APMs for your Payment Widget integration, use the cosssntact form" — activation is on SumUp's side, despite support initially saying none was needed. **Use this endpoint first** whenever a wallet/APM button is missing: get a checkout id by POSTing `{"order_items":[{"product_id":416,"quantity":1,"extras":[],"option":null}]}` (416 = "Brezel", 1 €) to the public `sumup-create-online-checkout` edge function with the anon key from `.env.local` (creates a harmless unpaid checkout). Apple Pay domain setup was already fine: dashboard → Einstellungen → Für Entwickler → Zahlungs-Wallets lists `immanuel-cafe.de`, and `/.well-known/apple-developer-merchantid-domain-association` is served (HTTP 200, same as `packages/frontend/public/.well-known/`). Apple Pay needs no `mount()` option; it only shows in Safari with a card in Wallet.
- **2026-08-24** — Migrations in `packages/supabase/migrations/` are never auto-applied (no CI/deploy hook). One sat unapplied and silently did nothing (an AppData row + a Switch in the UI that read it) until run manually via the Supabase Management API with `SUPABASE_ACCESS_TOKEN`, since no DB password was available for `supabase db push`. Full how-to: `docs/SUPABASE.md`.
- **2026-08-24** — `AppData` RLS is `authenticated`-only by default (one blanket policy). A public/unauthenticated page (e.g. `/menu`) reading it via the anon key silently gets `[]` — looks correctly wired in the frontend but never actually works for real customers. Needed a narrowly-scoped `anon` SELECT policy for just the one key that had to be public (table also holds `server_ip`/`server_port`, which must stay private). Full how-to: `docs/SUPABASE.md`.
- **2026-08-24** — `pnpm dev` binds port 3000 by default (`vite.config.ts`), but on this Mac port 3000 is held by an unrelated local project, and port 3001/3002 etc. get taken by any other concurrently-running `pnpm dev` for _this_ project (e.g. two agent sessions each running their own dev server) — Vite silently falls through to the next free port and prints the real URL in its own startup log. Don't assume `localhost:3000` when testing, and don't assume there's only one dev server instance running; read the actual `Local:` line, and check `lsof -i :<port>` if unsure.
- **2026-08-24** — `TABLE_NUMBERS` (was a static `Array.from({length: 30}, ...)` in `data/data.tsx`) has been replaced by `getTableNumbers(appData)` in `useAppData.tsx`, driven by the `table_count` AppData key (admin-editable on the Tisch-QR-Codes settings page, `pages/Settings/TableQrCodes.tsx` — moved there from Organisation settings since it's menu/table config, not org info). Any future code needing "all table numbers" should call `getTableNumbers(appData)`, not hardcode a range.
- **2026-08-24** — `useUpdateAppData` only does `.update().eq('key', key)` — no upsert. If the row doesn't exist yet (e.g. a just-added AppData key whose seed migration hasn't been pushed to the live DB), the update silently matches zero rows and still fires `onSuccess`/shows the success toast, even though nothing was saved. Always ship a seed migration (`INSERT ... WHERE NOT EXISTS`) alongside any new AppData key, and push it (see `docs/SUPABASE.md`) before relying on the settings UI for that key.
- **2026-08-24** — An admin settings input bound to an AppData value (e.g. Tisch-QR-Codes' "Anzahl Tische") writes on `onBlur`, not on an explicit save action. If two browser tabs/sessions have the same settings page open, the one with stale local state can silently overwrite a value the other tab just saved, whenever its input loses focus (tab switch, dev-server HMR reload, etc.) — observed `table_count` flip from a just-saved `26` back to the default `30` this way. Not a code bug per se, but worth checking for multiple open tabs before concluding a save "isn't sticking".
- **2026-08-24** — The app shell (`components/Navigation.tsx`) wraps routed content in `max-h-screen` + `overflow-y-auto` for the scrolling admin layout. Printing (`window.print()`) an overflow-auto container only prints the visible viewport-height slice, not the full scrollable content — this silently truncated the Tisch-QR-Codes print output. Fixed with `print:max-h-none print:overflow-visible` on that wrapper; any future page relying on `window.print()` benefits from this fix automatically, but keep it in mind if the wrapper is ever restructured.
- **2026-08-24** — Replaced the `qrcode.react` dependency with `qr-code-styling` (canvas/SVG QR codes with rounded dots, gradients, and a center logo/image, plus `getRawData()` to export PNG) for the café-branded Tisch-QR-Codes page (`pages/Settings/TableQrCodes.tsx` + `tableQrCodeStyle.ts`) — it was the only place using `qrcode.react`, so that dependency was removed rather than kept alongside.
- **2026-09-14** — PWA assets must live in `packages/frontend/public/`. `packages/frontend/img/` is a _sibling_ of `public/`, so Vite never copies it into `dist/` — the manifest's `/cafe/img/icons/*.png` entries were dead for months. It was invisible because nginx's `try_files $uri $uri/ /cafe/index.html` turns those 404s into `200 text/html` (the SPA shell), so the network tab shows no error, just a PNG that won't decode. `img/icons/` now lives in `public/img/icons/`; `img/CafeBlack.png` deliberately stayed put because `Statistic/GeneratePDF/OrdersPDF.tsx` bundles it via `import cafeImage from '/img/CafeBlack.png'`. When a static asset "exists but 404s", `curl -w '%{content_type}'` against prod is the fastest check — a `text/html` content type on an image URL means it's not in the build.
- **2026-09-14** — `<link rel="manifest" href="manifest.json">` (relative) in `index.html` only resolved on single-segment URLs like `/cafe/menu`; on every deeper route the browser requested e.g. `/cafe/admin/settings/manifest.json`, got the SPA HTML, failed to parse it, and `beforeinstallprompt` never fired. Vite **does** rewrite root-relative asset paths in `index.html` to the configured `base` (verified: `/manifest.json` → `/cafe/manifest.json` in `dist/index.html`), so always write these root-relative, never relative and never hardcoded to `/cafe`.
- **2026-09-14** — iOS ignores the web manifest entirely for "Zum Home-Bildschirm" — it needs `apple-touch-icon` plus `apple-mobile-web-app-capable`/`-status-bar-style`/`-title` in `index.html`. Also `display: "fullscreen"` is unsupported on iOS and hides the Android status bar; `standalone` is the right value here. - **2026-11-16** — TTS moved from OpenAI-on-the-Pi to OpenRouter via the `tts` edge function with a cached audio library (flow: `docs/PI5_SERVER.md`). Trigger: OpenAI credits ran out, but the old `/text-to-speech` answered HTTP 200 on every error, so nothing looked broken in the frontend — when audio is silent, check `docker logs cafe-app` first. OpenRouter has an OpenAI-compatible `POST /api/v1/audio/speech`, but **no OpenAI TTS models**, so `nova`/`alloy` voices won't carry over: each model has its own `supported_voices` (public list: `curl "https://openrouter.ai/api/v1/models?output_modalities=speech"`). German-capable picks: `microsoft/mai-voice-2.1-flash` (`de-DE-*` voices), `google/gemini-3.8-flash-tts`, `elevenlabs/eleven-multilingual-v2`. `GET /api/v1/key` with the key returns usage/limit, which works as a cheap "is the key valid and funded" test. OpenRouter answers a value that doesn't start with `sk-` (truncated key, key hash, `Bearer ` pasted twice) with a misleading `401 Missing Authentication header`, so `set-key` checks the `sk-or-` format first. Gemini TTS models only accept `response_format: "pcm"` (raw 24 kHz 16-bit mono) and say so in a 400; the `tts` function retries with the format named in that error and wraps PCM in a WAV header. The model dropdown on `settings/voice` is grouped by a hand-picked list in `pages/Settings/VoiceSettings/modelCatalog.ts` (OpenRouter gives no language metadata).
- **2026-11-16** — The daily order number used `MAX(order_number) % 100`; after order 99 the max stayed 99, so every further order that day got number 1 (busiest day: 124 orders). `migration_order_number_wraparound.sql` now continues from the most recent order (99 → 1 → 2 …). TTS pickup sets rely on numbers staying in 1–99.
- **2026-11-16** — TTS audio ids hash only (model, voice, text), so a sample "Bestellnummer 42 ist abholbereit!" made in the voice studio _is_ pickup audio 42. It stayed `kind = 'sample'`, the set counted 97/99 forever and "fehlende erzeugen" silently returned the cached sample. The `tts` function now adopts such a sample into the set (kind, order_number, pinned) when a set is generated.
